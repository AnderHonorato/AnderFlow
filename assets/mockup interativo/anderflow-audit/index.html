MÉDIO
Crítico #01
Server Components — App Router Mal Usado
Todas as páginas usam 'use client' desnecessariamente. O Next.js 14 App Router permite Server Components que eliminam JS do cliente para páginas estáticas.
● Crítico
PROBLEMA #01 — Arquitetura
Ausência total de Server Components
Páginas como changelog, audit-logs, analytics têm 'use client' mas não precisam. Isso força o Next.js a enviar todo o JavaScript dessas páginas para o browser, incluindo bibliotecas como lucide-react, recharts e framer-motion.
⚠ Impacto: Bundle +300KB desnecessário. TTI (Time to Interactive) 2–4x maior. Experiência degradada em mobile e conexões lentas.
App Router Performance Bundle Size Next.js 14
Arquitetura Atual (Errada) vs Arquitetura Correta
ATUAL — ERRADO
'use client' em tudo
changelog, audit-logs, analytics, automations...
→
Todo JS no cliente
Bundle ~500KB+ enviado ao browser
→
TTI Alto
3–5s em conexões lentas
CORRETO — SERVER COMP.
page.tsx sem 'use client'
Busca dados no servidor com Prisma
→
Props para Client
Apenas componentes interativos com JS
→
TTI <1s
HTML pronto no primeiro byte
// ❌ ATUAL: página estática com 'use client' desnecessário 'use client' export default function ChangelogPage() { // sem hooks, sem estado — 'use client' é inútil aqui return <div>...dados hardcoded...</div> } // ✅ CORRETO: Server Component com dados reais // page.tsx (sem 'use client') import { prisma } from '@/lib/prisma' import { ChangelogClient } from './changelog-client' export default async function ChangelogPage() { const releases = await prisma.release.findMany({ orderBy: { version: 'desc' } }) return <ChangelogClient releases={releases} /> }
Migrar 8 páginas estáticas para Server Components. Estimar redução de 60–70% no bundle JS enviado ao cliente.
Críticos #02–03
Bundle & Performance
Sem code splitting, todas as bibliotecas pesadas são carregadas no bundle inicial. Framer Motion, Recharts e Socket.IO somam ~270KB de JS desnecessário.
● Crítico
PROBLEMA #02 — Bundle
Sem Dynamic Imports / Code Splitting
framer-motion (~60KB), recharts (~170KB), socket.io-client (~40KB) são carregados em todas as páginas mesmo quando não são usados.
⚠ Bundle inicial estimado em 500KB+. Lighthouse Performance Score abaixo de 60 em mobile.
Bundle Size Dynamic Import Code Splitting
// ✅ dynamic import para Recharts const RevenueChart = dynamic( () => import('@/components/charts/revenue'), { ssr: false, loading: () => <Skeleton h="48" /> } )
● Crítico
PROBLEMA #03 — Data Fetching
useEffect + fetch em vez de React Query
Dashboard usa useEffect para buscar dados, causando double-render, flash de skeleton e sem cache. @tanstack/react-query está instalado mas não usado.
⚠ Usuário vê skeleton → dados toda vez que navega. Sem cache = dados re-fetched mesmo sem mudança.
// ✅ React Query com cache function useDashboard() { return useQuery({ queryKey: ['dashboard'], queryFn: () => fetch('/api/dashboard') .then(r => r.json()), staleTime: 30_000 }) }

Críticos #04–08
Segurança & Auth
APIs públicas sem proteção, validação ausente, secret JWT padrão e Socket.IO sem autenticação por token.
● Crítico
PROBLEMA #04 — Rate Limiting
Sem Rate Limiting nas APIs Públicas
Rotas /api/auth/register e /api/forgot-password completamente abertas para brute-force, spam de cadastro e DDoS em nível de aplicação.
⚠ Atacante pode criar 10.000 contas ou tentar 100K senhas sem bloqueio.
// ✅ middleware.ts com rate limiting const ratelimit = new Ratelimit({ redis: Redis.fromEnv(), limiter: Ratelimit.slidingWindow(10, '10 s'), })
● Crítico
PROBLEMA #05 — Validação
Sem Validação Zod nas APIs
Corpos de requisição chegam direto ao Prisma sem validação. Dados malformados causam erros 500 silenciosos ou comportamento inesperado.
⚠ Injection attacks, erros de runtime no Prisma, dados corrompidos no banco.
// ✅ Validação em toda API const schema = z.object({ name: z.string().min(1).max(100), clientId: z.string().cuid(), budget: z.number().positive().optional() }) const body = schema.parse(await req.json())
● Crítico
PROBLEMA #06 — Secret JWT
NEXTAUTH_SECRET Padrão e Inseguro
O .env contém NEXTAUTH_SECRET="super-secret-key-change-in-production" — uma chave conhecida publicamente. Sessions JWT podem ser forjadas.
⚠ Qualquer pessoa pode criar um token de admin válido e acessar o sistema.
● Médio
PROBLEMA #07 — Socket.IO Auth
WebSocket sem Autenticação por Token
O socket.ts do servidor não verifica identidade. Qualquer cliente pode conectar passando qualquer userId e receber mensagens de qualquer canal.
⚡ Vazamento de mensagens entre clientes. Falsificação de userId em tempo real.
// ✅ Socket com JWT verification io.use(async (socket, next) => { const token = socket.handshake.auth.token const user = await verifyJWT(token) if (!user) return next(new Error('Unauthorized')) socket.data.userId = user.id next() })
● Crítico
PROBLEMA #08 — CSP Headers
Sem Headers de Segurança HTTP
next.config.js sem Content-Security-Policy, X-Frame-Options, X-Content-Type-Options. Sistema vulnerável a clickjacking e XSS.
// ✅ next.config.js com headers async headers() { return [{ source: '/(.*)', headers: [ { key: 'X-Frame-Options', value: 'DENY' }, { key: 'X-Content-Type-Options', value: 'nosniff' }, ]}] }
Médios #09–12
Design System Incompleto
tailwind_config.ts tem apenas 3 cores e alguns border-radius. Sem tokens de spacing, typography, shadows ou animation. Cores hardcoded direto nos componentes.
● Médio
PROBLEMA #09 — Design System
Tokens de Design Ausentes
Cores HSL hardcoded nos componentes: hsl(228,88%,5%), hsl(222,47%,11%). Impossível fazer white-label ou mudar o tema sem busca e substituição global.
⚡ Inconsistências visuais acumulam. Qualquer mudança de marca exige refatoração massiva.
// ✅ design-tokens.ts export const tokens = { colors: { bg: { 0: 'hsl(228,88%,5%)', 1: 'hsl(222,47%,9%)' }, brand: { primary: 'hsl(217,100%,56%)' } }, radius: { sm: '10px', md: '14px', lg: '18px' }, spacing: { xs: '4px', sm: '8px', md: '16px' } }
● Médio
PROBLEMA #10 — Dialog
Dialog Customizado em Vez de Radix
dialog.tsx é um implementation customizada inferior. @radix-ui/react-dialog está instalado mas não usado. O customizado não tem focus trap, aria, scroll lock.
⚡ Acessibilidade comprometida. Screen readers anunciam incorretamente. Usuários de teclado presos.
● Médio
PROBLEMA #11 — Typography
Escala Tipográfica Não Definida
Todos os títulos usam text-2xl font-semibold. Sem distinção de h1/h2/h3. Fonte Inter não carregada via next/font — causa FOUT (Flash of Unstyled Text).
⚡ CLS (Cumulative Layout Shift) causado pelo carregamento tardio da fonte. Hierarquia visual fraca.
● Médio
PROBLEMA #12 — Card Variants
Card Sem Variantes de Espaçamento
card.tsx usa p-6 fixo, mas páginas sobrescrevem com p-4, p-5 via className. Sem sistema de variantes com cva para compact/default/relaxed.

Prisma & Banco de Dados
MELHORIA #42 — Índices Prisma
Schema Sem Índices — Full Table Scans
Nenhum @@index declarado no schema.prisma. Queries por clientId, userId, status serão full table scans conforme o banco cresce. Com 1000+ registros, queries de 500ms+ são comuns.
⚡ Performance degrada linearmente com crescimento dos dados. Dashboard com 10k registros pode travar.

MELHORIA #43 — SQLite → PostgreSQL
Unificar Provider em Dev e Produção
schema.prisma usa SQLite, .env referencia PostgreSQL. Tipos incompatíveis, enums fake, sem índices avançados. Unificar para PostgreSQL desde o desenvolvimento elimina surpresas em produção.

React Query & Type Safety End-to-End
MELHORIA #44 — React Query Pattern
Server State com React Query
@tanstack/react-query instalado mas subutilizado. Migrar todos os useEffect+fetch para useQuery/useMutation dá cache automático, refetch inteligente e optimistic updates.
// ✅ Hook reutilizável export function useProjects(filters?) { return useQuery({ queryKey: ['projects', filters], queryFn: () => api.projects.list(filters), staleTime: 60_000, gcTime: 5 * 60_000 }) } export function useUpdateProject() { const client = useQueryClient() return useMutation({ mutationFn: api.projects.update, onMutate: async (data) => { // optimistic update await client.cancelQueries(['projects']) const prev = client.getQueryData(['projects']) client.setQueryData(['projects'], old => ...) return { prev } } }) }
MELHORIA #45 — Type Safety E2E
tRPC ou Typed Route Handlers
api.ts faz fetch manual sem type safety. Com tRPC, o type do Prisma model é inferido automaticamente no frontend sem duplicação. Erros de type são detectados em tempo de compilação.
// ✅ Com tRPC — type inferido do Prisma // server: router/projects.ts export const projectsRouter = router({ list: publicProcedure .input(listProjectsSchema) .query(async ({ input }) => { return prisma.project.findMany(...) }) }) // client — tipo inferido automaticamente const { data } = trpc.projects.list.useQuery({ status: 'IN_PROGRESS' // TS valida aqui ✓ })
